## Analysis

Subsystems affected: **triggers (the most behaviourally significant change in
the range)**, property editor, maps, README.

**Phase F: trigger detection moves from per-tick to scheduled polling.**

What existed before → what replaced it:

* Baseline (`baseline.md` §7): `_handle_triggers` ran **every tick** (60 Hz),
  iterated all trigger brushes, tested only the **player** against cached
  float32 AABBs, and tracked enter/exit in `player_in_triggers`.
* **481 "Run all trigger detection at 1 Hz"** — all detection, player included,
  moves onto a scheduler. `TRIGGER_POLL_TICK = 0.25` wakes four times a second;
  a trigger is sampled when its own interval has elapsed (default 1.0 s).
* **483 "Vectorize complete trigger broad-phase"** — occupancy becomes one
  NumPy batch over (entities x triggers), with a filter mask per trigger
  (`player` = 1, `props` = 2, `monsters` = 4).
* 477/489/493/494: trigger **filters** — a trigger can now target props and
  monsters, not just the player. Damage is disabled and its state saved/restored
  when the props filter is selected (489, 493, 494).
* 484/486 "Clean up unified trigger state" / "Reset unified trigger polling
  state"; 485 tests that an unchanged trigger state emits no I/O.
* 487 "Fix trigger rewrite indentation error" — the rewrite did not parse.
* 499–501: **per-trigger poll interval** (`trigger_poll_interval`, snapped to
  1.0 / 0.5 / 0.25).

**This is the change that cost the most and was tested the least.**

1. **CONFIRMED REGRESSION, user-reported, fixed in this audit (commit 481):**
   the rewrite made `_handle_triggers` assign `current_hud_message =
   self._trigger_use_prompt` **unconditionally**. It runs after
   `_handle_interactions` and `PropSession.tick`, so an empty sample wiped every
   prompt they had just published: `"NEED: <key>"`, `"[E] Open"`,
   `"[E] Unlock (...)"`, `"[E] Pick up ..."`, `"[E] Complete Level"`,
   `"[E] Drop"`. At baseline the assignment lived inside the in-range branch and
   could only ever *add* a prompt. See regressions.md REG-01.

2. **Latency, inherent to the design and still present:** a use-trigger's
   `[E] ...` prompt is now a value *sampled* at the trigger's poll interval, so
   it can appear up to 1 s late and linger up to 1 s after the player turns
   away. The facing test uses the player angle **as it was at the poll**, not
   the live one. Recorded in regressions.md REG-02 as a design consequence
   rather than a bug to patch blind — restoring per-frame responsiveness means
   re-introducing per-tick work for use triggers specifically.

3. **Float boundary (fixed):** the per-trigger interval comparison carried a
   `1.0e-9` tolerance; the scheduler-tick comparison did not. 60 frames of
   `1/60` sum to `0.99999999999999989`, so a 1 Hz trigger lost one scheduler
   step per second and drifted. Both now share `TRIGGER_POLL_EPSILON`.

4. **`_trigger_poll_interval` snaps rather than validates:**
   `min(allowed, key=lambda i: abs(i - value))` silently rewrites an authored
   `2.0` to `1.0` and `0.1` to `0.25`, and resolves the exact midpoint `0.375`
   by iteration order. Not a defect (the docstring says "return a valid
   interval") but a map can author a cadence it does not get. Recorded in
   compatibility.md.

5. **Test coverage: `tests/logic/test_trigger_filters.py` had never passed.**
   It errored on import at the commit that added it (482) and failed 4/4 from
   487 onward, because 499–501 added scheduler state (`_trigger_poll_elapsed_by_bid`,
   `_trigger_use_seen`, `_trigger_use_prompts`) the helper never constructed,
   and its `Vec` stub was not a sequence the vectorised broad-phase could accept.
   Repaired in this audit; HUD regression tests added.

Performance: the intent is sound — the baseline's per-tick scan over all
triggers is real work, and batching plus scheduling removes it. The cost was
paid entirely in gameplay responsiveness and in a HUD regression that shipped.
